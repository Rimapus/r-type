Abstract

   This document specifies the UDP protocol between the J-Type server
   and its clients.  It defines the packet header, the session handshake
   and keepalive, every game message, the way a snapshot is split into
   datagrams, and the rules a receiver applies to what it accepts.  It
   is the reference for writing another client for a J-Type server.

1.  Introduction

   J-Type is a networked shoot'em up for up to four players.  One server
   owns the game: it moves the ships, decides what the missiles hit,
   keeps the score and sends the world to every client.  A client reads
   the keys, sends them, and draws what the server sends.  This document
   describes the bytes they exchange.

   The engine provides the datagram envelope and the session layer.  The
   game puts one message in each GameData packet.  The protocol is state
   based: the server repeats the whole world and the whole score at
   every step, and the events only announce a change that the state of
   the same step already carries.

1.1.  Requirements Language

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in BCP
   14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

1.2.  Scope

   This document covers version 1 of the protocol.  It does not describe
   the rules of the game, the assets, the rendering, or the C++ API of
   the implementation.  The values of the game, such as the points a
   Bydo is worth, are part of the game and not of the wire format.

2.  Transport and Framing

   The protocol runs over UDP [RFC768].  A datagram carries exactly one
   packet.  IP fragmentation is avoided: a datagram MUST NOT exceed 1200
   bytes including the packet header, so it fits in the usual 1500-byte
   Ethernet MTU after the IP and UDP headers.






Tutti, et al.                 Informational                     [Page 2]

                             J-Type Protocol               November 2026


   UDP does not deliver, order or deduplicate datagrams.  A receiver
   MUST tolerate loss, reordering and duplication.  The protocol does
   not retransmit lost game messages: the next state makes up for a lost
   one, as described in Section 7.

   All multi-byte integer fields are unsigned and encoded in little-
   endian order, least significant byte first.  Floating-point fields
   are IEEE 754 binary32 values [IEEE754], also little-endian.  A
   receiver MUST reject a non-finite floating-point field.

3.  Packet Header

   Every datagram starts with the 8-byte header of the engine.  The
   fields are:

      +==========+======+=======+===================================+
      | Field    | Type | Bytes | Value                             |
      +==========+======+=======+===================================+
      | Magic    | u16  | 2     | 0x3659, the bytes 0x59 0x36, "Y6" |
      +----------+------+-------+-----------------------------------+
      | Version  | u8   | 1     | 1                                 |
      +----------+------+-------+-----------------------------------+
      | Type     | u8   | 1     | See Table 2                       |
      +----------+------+-------+-----------------------------------+
      | Sequence | u32  | 4     | Sequence number of the sender     |
      +----------+------+-------+-----------------------------------+

                       Table 1: Packet Header Fields

   The magic number rejects traffic from another application before any
   parsing.  A datagram whose magic, version or type is unknown, that is
   shorter than the header, or that is longer than 1200 bytes MUST be
   dropped silently.  The sequence number is a counter of the sender for
   each peer, starting at 0, increased by one for each packet sent to
   that peer, session packets and game messages alike, and wrapping
   modulo 2^32.  It lets the peer detect loss; the protocol does not
   acknowledge or retransmit game messages.

   A Ping or a Pong MUST carry exactly 4 payload bytes; a Connect, a
   ConnectAck or a Heartbeat MUST carry none.  A packet that breaks
   these rules MUST be dropped.  The payload of a GameData packet is
   decoded as described in Section 5.

4.  Session

   The session layer keeps track of the peers and of their liveness.  A
   client MUST NOT send a game message before its session is open, and a
   server MUST drop a game message that comes from an endpoint without a
   session.

4.1.  Handshake

   The client sends a Connect and waits for a ConnectAck.  It repeats
   the Connect until the server answers, so a lost Connect or ConnectAck
   only delays the handshake.  The server answers every Connect from a
   known or a new endpoint with a ConnectAck and a Connect resets the
   sequence number that the server uses for that endpoint to 0.

   The server keeps at most 1024 sessions.  A Connect from a new
   endpoint while the table is full is dropped without an answer.  A
   session ends when the peer stays silent for 3000 ms; a Leave frees
   the player's slot at once, without waiting for the timeout.



Tutti, et al.                 Informational                     [Page 4]

                             J-Type Protocol               November 2026


4.2.  Keepalive

   Once the session is open, the client sends a Heartbeat every 500 ms.
   The server answers each Heartbeat with a Heartbeat, so the client
   keeps hearing from the server even when the game sends nothing.  A
   peer MAY also send a Ping every 1000 ms; the peer answers with a Pong
   carrying the same cookie, and the sender measures the round trip.

   Any valid packet from a known peer refreshes its session, not only a
   Heartbeat.  A heartbeat interval is shorter than the timeout, so
   several heartbeats fit in one timeout and a single lost datagram does
   not end a healthy session.

5.  Game Messages

   A GameData payload holds exactly one game message.  Its first byte is
   the message type; the fields follow, in the order of this document.
   A decoder MUST reject an empty payload, an unknown type, a field that
   runs past the payload, a value outside its range, and a payload with
   bytes left after the last field.

5.2.  Join

   The client sends a Join once its session is open, and repeats it
   every 500 ms until the server answers with a Welcome or a Full.  A
   client that already holds a slot gets that slot in a new Welcome.  A
   Join starts a new stream of inputs: the server forgets the last input
   step it accepted from the client.

   the keys held down and the step of the client.  The server applies an
   input to the ship of the slot that owns the endpoint; the wire

   and increases it by one for each Input it sends; the counter wraps
   modulo 2^32.  The server keeps the last tick it accepted for the
   client, resets it on a Join, and drops an Input whose tick is not
   newer under the serial comparison of Section 7.  The server applies
   the input to the ship during the next step, and gives its tick back
   in the Last input field of the snapshots it sends to that client.

5.5.  Snapshot

   The server sends a snapshot at each of its steps.  A snapshot is the
   whole world: every entity the clients must draw.  When the entities
   do not fit in one datagram, the server splits the snapshot into
   chunks, as described in Section 6; every chunk carries the same tick,
   the same last input and the same counts.

   The client sends a Leave when it quits.  The server frees the slot at
   once, removes the ship, and tells the other clients with a
   PlayerDisconnected event and the next scoreboard.  A client that
   never joined MAY send a Leave; the server ignores it.

5.9.  Spawn

6.  Snapshots and Chunking

   The game runs on fixed steps of 1/60 s on both sides.  The server
   starts its tick at 0, increases it by one at each step, and wraps it
   modulo 2^32.  A snapshot, the events of the step and the scoreboard
   all carry the tick of the step they describe.

   After the 8-byte packet header and the 15-byte snapshot header, 14
   bytes per entity fit in a datagram of at most 1200 bytes.  Therefore
   a chunk carries at most 84 entities:

   floor((1200 - 8 - 15) / 14) = 84









Tutti, et al.                 Informational                    [Page 17]

                             J-Type Protocol               November 2026


   A snapshot of n entities is split into max(1, ceil(n / 84)) chunks,
   numbered 0 to chunk count minus 1.  The chunk of index i carries the
   entities from i * 84 to min((i + 1) * 84, n) - 1, in snapshot order.
   The count field of the chunk is the number of entities it carries, so
   the last chunk may be shorter.  A snapshot holds at most 64 chunks,
   or 5376 entities; a larger snapshot is not sent.

   An empty snapshot is legal: the server sends one chunk with chunk
   count 1, index 0, entity count 0 and count 0.  A client MUST treat it
   as an empty world, not as a missing snapshot.

   A chunk is valid only when its chunk count is 1 to 64, its index is
   below its chunk count, its entity count is at most 5376, its chunk
   count is exactly the one the entity count implies, and its count is
   exactly the number of entities the index implies.  A chunk that
   breaks one of these rules MUST be dropped.  A client reassembles the
   chunks of one tick, drops a duplicated index, and discards a snapshot
   whose chunks disagree on the entity count or the chunk count.  An
   incomplete snapshot is discarded when newer ones replace it; the next
   complete snapshot carries the whole world anyway.

7.  Reliability and Ordering

   The protocol has no acknowledgement and no retransmission of game
   messages.  It relies on two properties:

   *  Every message that carries state carries the whole state of its
      kind: a snapshot is the whole world and a scoreboard is the whole
      score.  A lost one is replaced by the next one, 1/60 s later.

   *  An event only announces a change that the snapshot or the
      scoreboard of the same step already carries.  A lost event delays
      a sound or an effect, and never changes the game.

   Join is the only game message that needs an answer.  The client
   repeats it every 500 ms until a Welcome or a Full arrives.  Connect
   and Heartbeat are repeated by the session layer as described in
   Section 4.

   Snapshots can arrive out of order.  A client keeps the snapshots in
   the order of their tick, and draws the world a few steps behind the
   newest snapshot so it can interpolate between two known states.  The
   number of steps of delay is a client choice; it does not change the
   wire format.

7.1.  Comparing Ticks

   A tick is a 32-bit counter that wraps.  Two ticks are compared with
   serial number arithmetic [RFC1982]: a is newer than b when the signed
   32-bit value of a - b is positive.  For example, 0 is newer than
   0xFFFFFFFF, and 0xFFFFFFFF is not newer than 0.  Two equal ticks are
   not newer than each other.

   The server uses this comparison for the tick of an Input.  It accepts
   the first Input of a client, then only an Input whose tick is newer
   than the last one accepted; a duplicated or reordered Input is
   dropped.  A Join resets the comparison, so a client that starts its
   ticks again is accepted.

8.  Validation and Error Handling

   A receiver validates each layer in order and drops what it cannot
   accept.  It MUST NOT crash, block or allocate without bound on a
   malformed or hostile datagram.

       +====================+=====================================+
       | Reason             | Cause                               |
       +====================+=====================================+
       | Not a game message | The packet is not a GameData packet |
       +--------------------+-------------------------------------+
       | Empty              | The payload holds no message type   |
       +--------------------+-------------------------------------+
       | Unknown type       | The type byte is not 1 to 13        |
       +--------------------+-------------------------------------+
       | Truncated          | A field ends after the payload      |
       +--------------------+-------------------------------------+
       | Invalid value      | A slot, a type, a state, an input   |
       |                    | bit or a float is out of range      |
       +--------------------+-------------------------------------+
       | Trailing bytes     | The payload goes on after the last  |
       |                    | field                               |
       +--------------------+-------------------------------------+
       | Invalid chunk      | The fields of a snapshot chunk do   |
       |                    | not agree with its entity count     |
       +--------------------+-------------------------------------+

                     Table 25: Message Decode Errors

                             J-Type Protocol               November 2026


   The server drops a datagram whose header fails, then a game message
   that fails to decode, and counts it.  It prints the count and the
   first reason at most once a second, so a flood cannot flood the log
   too.  A game message from an endpoint without a session is dropped.
   An Input from an endpoint without a slot is ignored, and an Input
   whose tick is not newer than the last one accepted is ignored.

   To bound the work of one receive call, the server handles at most 256
   datagrams per call; the rest waits for the next call.  It queues at
   most 256 events per step; an event past that is dropped, and the
   state still carries the change.  Its incoming and outgoing datagram
   queues hold at most 1024 datagrams, and its session table holds at
   most 1024 peers.

   A client applies the same strictness: it drops a datagram from
   another address than its server, a packet the header rejects, and a
   game message the decoder rejects.  It keeps the snapshots in the
   order of their tick and never draws the world backwards, so a
   duplicated or late snapshot has no effect on the picture.

10.  Security Considerations

   The protocol has no authentication and no encryption.  A player is
   identified by the source address of its datagrams, and a UDP source
   address can be written by anyone.  Someone who knows the address of a
   player can send Inputs or a Leave in their name, and an Internet-
   reachable server can be filled with fake sessions or fake players
   until the four slots are taken.  The protocol is meant for a game on
   a local network.







Tutti, et al.                 Informational                    [Page 21]

                             J-Type Protocol               November 2026


   The server is authoritative: a client sends only the five input bits,
   its own tick and its own Join or Leave.  It cannot set a position, a
   health, a score, a killer or a slot on the wire.  The server computes
   the game from the inputs it accepts.

   A receiver bounds what an incoming datagram can make it allocate: the
   packet size is limited to 1200 bytes, the snapshot entity count to
   5376, the session table to 1024 peers, the datagram queues to 1024
   entries, and the events of a step to 256.  A malformed datagram is
   dropped and counted, and its processing never throws.

   The server logs the address of a joining player and a rate-limited
   summary of rejected datagrams.  It logs no payload and keeps no log
   file; an operator who needs more keeps the standard output or adds
   counters.
